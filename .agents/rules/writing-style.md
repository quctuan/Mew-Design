# Design writing style

Use the language requested by the designer and keep interface copy in the product's target language. Code, variable names, and node IDs stay as they are.

Write less without losing meaning: compress, do not omit. Keep the decision, its reason, warnings, relevant IDs, and what is blocking. Cut introductions, restatements of what was just done, lists of files read, and second explanations of a decision already stated. This applies to Markdown files as much as to chat; a long document nobody reads is worth nothing.

Use one main idea per paragraph or line. Tables help compare screen variants or map current copy to proposed copy, but do not turn every answer into a table. When the designer must decide something, ask directly in one or two sentences at the end. Refer to exact screen or node IDs only when they help the reader find the work; keep project-specific IDs in private project files.

For handoff, distinguish what is approved from what is still exploratory. Put implementation values where engineers can find them and keep design-process history in a separate decision log.
